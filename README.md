# Душевые / Станок

Производство и продажа душевых ограждений под проём: витрина, конфигуратор чернового КП и личные кабинеты по ролям. Каталог комплектующих собирается парсерами поставщиков и отдаётся API.

**GitHub — источник правды** для кода и документов (`maxim59901/dushevye`). Шар и VDS — рабочие копии, не место, откуда берётся история.

Сайт лежит в `public/` (так его отдаёт nginx: корень `/var/www/dushevye/public`). Раньше `index.html`, `cfg.html` и `lk/` лежали в корне репозитория — это ранний снапшот. Сейчас их место только `public/`. `DEVELOPMENT.md` остаётся в корне.

## Состав

| Путь | Что это |
|---|---|
| `public/` | Витрина (`index.html`, помощник), конфигуратор (`cfg.html`), ЛК (`public/lk/`) |
| `app/` | FastAPI: вход, роли, журнал, каталог (`/api/*`) |
| `parsers/` | Импорт прайсов поставщиков в CSV / `parts.json` |
| `data/` | Сырые CSV и JSON каталога. SQLite (`*.db`) в git не входит |
| `docs/` | Роли, auth, парсеры, бэкапы |
| `deploy/` | nginx, systemd, скрипт установки на VDS, выкладка по SSH |
| `DEVELOPMENT.md` | Разбор фронтенда и план. Безопасность P1 ещё не закрыта |

Фото товаров (`public/media/parts/`) в репозиторий не кладём.

## Локальный API

Нужен Python 3.11+. Секрет сессии и базы задаются окружением, не файлом в git.

```bash
python3 -m venv .venv
.venv/bin/pip install -r app/requirements.txt
export DUSHEVYE_SESSION_SECRET=dev-only-not-for-production
export DUSHEVYE_DB="$PWD/data/app.db"
export DUSHEVYE_CATALOG_DB="$PWD/data/catalog/catalog.db"
export DUSHEVYE_ADMIN_PASS_FILE="$PWD/secrets/initial-admin.txt"
mkdir -p secrets data/catalog
.venv/bin/python -m app.seed
.venv/bin/python -m app
```

API слушает `127.0.0.1:8088` (`/api/health`). Стартовый пароль админа скрипт пишет в `secrets/initial-admin.txt` и печатает в консоль один раз — этот файл в `.gitignore`.

Каталог (`/api/catalog`) читает SQLite. Файла `catalog.db` в git нет: его собирает `python -m parsers` (зависимости в `parsers/requirements.txt`) в `data/catalog/catalog.db`. Пока базы нет, каталог отвечает 503, auth при этом работает.

## Конфигуратор КП

`public/cfg.html` — черновик спецификации. Стекло: площадь проёма × ставки `GLASS_RATES` в этом файле (оценка, в строке BOM так и подписана). Фурнитура: позиции `GET /api/catalog` (фильтры `group`, `source`, `q`). В сумму попадает поле `price` из ответа. Демо-наборы «базовый / усиленный» удалены.

Закуп в JSON видят admin, owner и accountant — как в ЛК. У остальных ролей `price` пустой: позицию можно добавить в спецификацию, итог она не увеличивает.

Один origin для страницы и cookie (на VDS это уже делает nginx; локально — флаг ниже). `DUSHEVYE_SERVE_PUBLIC` на сервере не включайте.

```bash
export DUSHEVYE_SESSION_SECRET=dev-only-not-for-production
export DUSHEVYE_DB="$PWD/data/app.db"
export DUSHEVYE_CATALOG_DB="$PWD/data/catalog/catalog.db"
export DUSHEVYE_ADMIN_PASS_FILE="$PWD/secrets/initial-admin.txt"
export DUSHEVYE_SERVE_PUBLIC=1
mkdir -p secrets data/catalog
.venv/bin/python -m app.seed
.venv/bin/python -m app
```

Откройте http://127.0.0.1:8088/cfg.html . Без сессии каталог отвечает 401 — кнопка «Войти» возвращает на конфигуратор (`/lk/login.html?next=/cfg.html`). Пароль админа лежит в `secrets/initial-admin.txt`. Дальше: шаблон, размеры по его полям, группа фурнитуры (петли, ручки, уплотнители…), поиск, «Добавить в КП». В превью — стекло и фурнитура (артикул, название, количество, цена, сумма) и итог.

## Шаблоны и правила

Справочник из четырёх шаблонов лежит в коде (`app/config_rules.py`), не в `catalog.db`. `GET /api/templates` отдаёт его без сессии.

| id | Конструкция | Размеры | Угол ≠ 90° |
|---|---|---|---|
| `corner_two` | Угловая, две стенки: глухая + дверь | A, B, высота | нет |
| `niche_straight` | Прямая ниша, одна или две створки | ширина проёма, высота | нет |
| `ushape` | П-образная: бок, фасад с дверью, бок | B, A, C, высота | нет |
| `trapezoid` | Трапеция | A, B, высота, угол | да |

У каждого шаблона свои мин/макс и допустимая толщина стекла (8 или 10 мм). Площадь и ставка стекла те же, что раньше: угловая считается как прежняя `corner`, ниша — как `straight`. П-образная и трапеция добавляют свой коэффициент в `GLASS_RATES`, формула площади рядом с остальными.

`POST /api/config/validate` (сессия и `X-CSRF-Token`) принимает `template_id`, размеры, стекло и выбранные `part_ids` или `items` с количеством. Ответ: `ok`, `errors[]`, `warnings[]`, у каждого пункта `code` и русский `message`. Ошибки — размер вне допуска, толщина не из списка шаблона, петля или зажим не под эту толщину, несовместимая пара (раздвижная система вместе с петлями или зажимами), прямой угол на трапеции, слишком мало петель, если петли уже выбраны. Предупреждения не блокируют: петель ещё нет, зажимов на глухую панель меньше порога. Пороги — таблица по высоте и ширине створки, без расчёта веса. Новое правило добавляется словарём в `THICKNESS_RULES` или `PAIR_RULES` (группа, фрагмент артикула/названия или список `part_ids`). Содержимое каталога поставщиков не меняется.

В конфигураторе шаблон — первый шаг, поля размеров строятся по нему. Ошибки видны до «Сохранить КП», кнопка при ошибке неактивна. Замечание (жёлтый блок) сохранение не запрещает.

## Правила каталога

Поверх четырёх шаблонов — фильтр позиций по текущему стеклу и типу конструкции. Словарь в `app/config_rules.py` по-прежнему проверяет уже выбранную фурнитуру. Дополнительно таблица `catalog_compat_rules` в `app.db`: стартовая матрица «группа × толщина» (петли, зажимы, уплотнители, профиль) и правила «дверь / глухая панель». Своё правило добавляет админ или хозяин, код для этого менять не нужно. `catalog.db` только читается: в правиле группа, фрагмент названия или `part_id`.

`GET /api/catalog/compat?glass_mm=&template_id=` доступен любой вошедшей роли. В ответе группы `allow`/`deny` и список позиций `deny` с короткой причиной. Конфигуратор серит такие строки и не даёт добавить их в КП. Уже лежащая в спецификации позиция остаётся: количество и цена считаются как раньше, сохранить несовместимый набор нельзя.

Стекло 6 мм (в списке толщин оно есть, шаблоны его не принимают): петля серии «только 8/10» серая, `POST /api/config/validate` падает. 8 и 10 мм по-прежнему единственные толщины, с которыми КП сохраняется.

Список, создание и удаление: `GET/POST /api/catalog/compat/rules`, `DELETE /api/catalog/compat/rules/{id}`. Менять могут admin и owner, на запись нужен `X-CSRF-Token`. Менеджер получает 403 и видит только серые позиции в конфигураторе. Страница — `/lk/catalog-rules.html`.

```bash
.venv/bin/python tests/test_catalog_compat.py
.venv/bin/python tests/test_config_rules.py
```

Проверка API:

```bash
.venv/bin/pip install -r app/requirements.txt httpx
.venv/bin/python tests/test_config_rules.py
```

## Помощник витрины

На главной (`public/index.html`) плавает панель «Помощник» — скрипт `public/vitrine-chat.js`. Блоки лендинга не перестроены. Цвета те же, что у витрины: графит и один оранжевый акцент. Мессенджеры на витрину не добавляются.

Гость пишет тип и размеры. `POST /api/vitrine/chat` без сессии и без CSRF: у гостя нет куки, токен сессии тут не к чему привязать. Лимит — 10 запросов в минуту с одного адреса. Адрес берётся из `X-Real-IP` (nginx подставляет `$remote_addr` и затирает значение клиента). Первый адрес из `X-Forwarded-For` не используется: его можно подделать. На 11-м запросе ответ `429` и заголовок `Retry-After: 60`. Тот же лимит у заявки, но ведро отдельное: переписка не съедает попытки формы.

Ответ сначала собирают правила в `app/vitrine.py`, без внешнего ключа:

- угловая, ниша, П-образная или трапеция и числа в миллиметрах → шаблон из `app/config_rules.py` и ссылка на конфигуратор;
- «угловая 900×900» → шаблон `corner_two`, ширина A 900 мм, глубина B 900 мм, ссылка `/cfg.html?template=corner_two&width_mm=900&depth_mm=900`. Высоты в фразе нет — её просят указать в конфигураторе (для шаблона 1800–2200 мм). Конфигуратор читает эти параметры при открытии;
- «что такое КП», сроки изготовления, как попасть в демо кабинета;
- точную цену и закуп помощник не считает и не показывает. Сумма живёт в конфигураторе (стекло по ставкам страницы, фурнитура из каталога после входа).

Если в окружении есть `OPENAI_API_KEY`, черновик можно переформулировать. Совместимый адрес — `OPENAI_BASE_URL` (по умолчанию `https://api.openai.com/v1`), модель — `OPENAI_MODEL` (по умолчанию `gpt-4o-mini`). `DUSHEVYE_VITRINE_LLM=0` оставляет только правила, даже когда ключ задан. Текст модели с ценой, ссылкой или мессенджером отбрасывается, гость видит черновик правил. Кнопки и id шаблона модель не выбирает.

Внизу панели две кнопки исхода. «Оставить заявку» — имя, телефон, комментарий — уходит в `POST /api/vitrine/leads`. «Демо ЛК» ведёт на `/lk/login.html`: отдельной саморегистрации нет, учётку по-прежнему создаёт админ или хозяин.

Заявка пишется в таблицу `vitrine_leads` (та же SQLite, `DUSHEVYE_DB`), не в `projects`. У проекта обязателен автор-пользователь, а гостя на витрине нет. Статус в строке всегда «заявка с витрины», поле из запроса его не меняет. Организация — запись со slug `default`, иначе первая в базе. В журнале событие `vitrine_lead` без actor. Страницы этих заявок в ЛК нет.

Проверка:

```bash
.venv/bin/pip install -r app/requirements.txt httpx
.venv/bin/python tests/test_vitrine_chat.py
```

Локально вместе со страницей (как в блоке «Конфигуратор КП», с `DUSHEVYE_SERVE_PUBLIC=1`): откройте http://127.0.0.1:8088/ , кнопка «Помощник», фраза «угловая 900×900», затем «Открыть конфигуратор» и «Оставить заявку».

## Сохранение КП и PDF

Черновик пишется в ту же SQLite, что и учётки (`DUSHEVYE_DB`, таблицы `quotes` и `quote_items`). Организация и автор берутся из сессии, не из тела запроса. Цена фурнитуры тоже: сервер ещё раз читает каталог и сохраняет снимок (id, количество, артикул, название, закуп). Клиентская цена игнорируется. Стекло сервер считает теми же ставками, что `GLASS_RATES` в `cfg.html`.

`POST /api/quotes` требует заголовок `X-CSRF-Token` (`GET /api/auth/csrf`), как вход. Если в теле есть `template_id`, сервер прогоняет те же правила, что `/api/config/validate`. При `errors` ответ 400, строка КП не пишется. Отдельного обхода нет. Старый запрос без `template_id` (прежние типы corner / straight / niche / sliding / accordion) сохраняется как раньше.

Кто видит черновик:

| Роль | Список и карточка | Цены закупа в ответе и PDF |
|---|---|---|
| admin, owner | все КП своей организации | да |
| accountant | только свои | да |
| manager и остальные | только свои | нет: в PDF состав BOM, в итоге только оценка стекла |

Чужое или чужой организации КП отвечает 404.

PDF: `GET /api/quotes/{id}/pdf` открывает файл в браузере, `?download=1` отдаёт его как скачивание. Сборка на `fpdf2` (чистый Python, без WeasyPrint). Нужен TTF с кириллицей: на Ubuntu это пакет `fonts-dejavu-core` (DejaVu Sans). Если шрифта нет, PDF отвечает 503, сама запись КП остаётся.

Кнопка «Сохранить КП» в `cfg.html` появляется у расчёта. После сохранения — ссылки «Открыть PDF» и «Скачать PDF» и строка в блоке «Сохранённые КП». «Печать черновика» по-прежнему печатает текущий экран через `window.print()`, без записи в базу.

Как проверить локально (после команд из блока «Конфигуратор КП» выше, сервер с `DUSHEVYE_SERVE_PUBLIC=1`):

1. Откройте http://127.0.0.1:8088/cfg.html , войдите, добавьте позицию из каталога.
2. «Сохранить КП». Внизу страницы строка в списке, ссылки открывают PDF со стеклом и фурнитурой (артикул, количество, сумма).
3. Выйдите и войдите менеджером, которого создал админ. В списке только его КП; в PDF позиции есть, закупа нет. Админ в том же списке видит и своё, и менеджерское, с закупом.
4. `GET /api/catalog` и вход без этих шагов работают как раньше. В журнале админа есть событие `quote_create`.

## Проекты (воронка)

Карточка клиента живёт в той же SQLite (`DUSHEVYE_DB`, таблица `projects`): организация, имя / телефон / адрес, ответственный, автор, статус, необязательное КП, сумма, срок, даты создания и изменения. Статус при создании всегда «Создан». Дальше его можно поставить на любой шаг:

Создан → Просчёт → В работе → Чертёж → Фурнитура → Завершено → Архив.

Рекламации в этом шаге нет. Удаления проектов нет: конец воронки — «Архив». При переходе в «Завершено» или «Архив» пишется `closed_at`; возврат на рабочий шаг его снимает.

Кто что видит:

| Роль | Список и карточка | Менять статус и привязывать КП |
|---|---|---|
| admin, owner | все проекты организации | да, и можно назначить ответственного |
| manager | где он автор или ответственный | да, только эти |
| accountant | все проекты организации | нет |
| остальные | где назначены ответственным | да, только эти |

Чужой проект отвечает 404. Бухгалтер на изменение получает 403.

`POST /api/projects`, `PATCH /api/projects/{id}/status` и `PATCH /api/projects/{id}/quote` требуют `X-CSRF-Token`. В журнале: `project_create` и `project_status_change` (текст вида «Создан -> Просчёт»). Смена статуса, создание и привязка КП дополнительно пишут строку в `entity_versions` с полями до и после — см. «Версии сущностей».

Страница: `/lk/projects.html`. Ссылки стоят в кабинетах админа, хозяина и менеджера. Фильтры — статус и клиент (имя или телефон). В карточке — смена статуса и привязка КП из списка, который роль и так видит в `/api/quotes`. Ссылка «КП №…» открывает PDF.

В конфигураторе (`cfg.html`) после входа есть список своих проектов. Выбранный проект получает КП при «Сохранить КП» (`project_id` в `POST /api/quotes`). Уже сохранённое КП привязывается кнопкой «Привязать уже сохранённое КП».

Как проверить локально (сервер с `DUSHEVYE_SERVE_PUBLIC=1`, как в блоке «Конфигуратор КП»):

1. Войдите админом и откройте http://127.0.0.1:8088/lk/projects.html (или пункт «Проекты» в кабинете).
2. Создайте проект: клиент, телефон, адрес. В списке статус «Создан».
3. Поставьте «Просчёт», затем дойдите до «Архив». Смена без CSRF-токена отвечает 403. В журнале админа есть `project_create` и `project_status_change`.
4. Откройте http://127.0.0.1:8088/cfg.html , выберите этот проект, сохраните КП. В карточке проекта появляется ссылка на PDF. То же самое делается из карточки: выбрать КП и «Привязать КП».
5. Создайте менеджера и бухгалтера. Менеджер видит только свои проекты и может двигать их статус. Бухгалтер видит все проекты организации и не может создать или сменить статус. Замерщик видит проект, только если он в нём ответственный.

## Склад комплектующих

Остатки живут в `app.db` (`stock_balances`, `stock_movements`) и ссылаются на `part_id` каталога. `catalog.db` открывается только на чтение: приход не меняет цены, названия и остатки поставщика. В списке склада только позиции, которые уже оприходовали, а не все 3165 строк каталога.

На балансе: остаток (`qty_on_hand`), резерв (`qty_reserved`), минимум (`min_qty`). Свободно = остаток − резерв. Дефицит = насколько свободно не дотягивает до минимума (если свободно больше минимума, дефицит 0). Сортировка списка фиксированная: больший дефицит, затем больший резерв, затем меньший остаток, затем больший минимум.

Движение (`stock_movements`): приход `in`, расход `out`, резерв `reserve`, снятие `release`. У каждого есть количество, необязательный `project_id`, автор (`actor_id`), комментарий и время. Расход списывает только свободный остаток и сам резерв не снимает. Снять резерв можно только из той же привязки: с проекта — по этому `project_id`, без проекта — отдельным движением без проекта.

| Роль | Остатки | Приход и расход | Резерв |
|---|---|---|---|
| admin, owner, supply | вся организация | да | да, проект необязателен |
| manager | вся организация | нет | да, только под свой проект (автор или ответственный) |
| accountant | вся организация | нет | нет |
| measurer, installer, production | нет | нет | нет; видят резерв проектов, где они ответственные |

Чужой проект для менеджера отвечает 404. Мутации без `X-CSRF-Token` отвечают 403. В журнале: `stock_in`, `stock_out`, `stock_reserve`, `stock_release` (в деталях артикул, количество и номер проекта, если он есть). Те же операции пишут версию остатка: `qty_on_hand`, `qty_reserved`, `min_qty`.

Страница: `/lk/stock.html`. Ссылки стоят в кабинетах админа, хозяина, снабжения и менеджера. Жёлтая строка — свободный остаток ниже минимума. Позицию для прихода ищут в каталоге, кнопки в строке подставляют её в форму.

Как проверить локально (сервер с `DUSHEVYE_SERVE_PUBLIC=1`, как в блоке «Конфигуратор КП»; нужен собранный `catalog.db`):

1. Войдите админом или снабжением и откройте http://127.0.0.1:8088/lk/stock.html (или пункт «Склад» в кабинете).
2. Найдите позицию каталога, укажите количество и минимум, нажмите «Оприходовать». В таблице появляются остаток и, если свободно меньше минимума, жёлтая строка дефицита.
3. Создайте проект и зарезервируйте часть остатка под него. Свободно уменьшается, резерв растёт. Списание больше свободного остатка отвечает 400, пока резерв не снят.
4. Запрос без CSRF-токена отвечает 403. В журнале админа есть `stock_in` и `stock_reserve`.
5. Войдите менеджером: приход и расход скрыты, резерв проходит только под свой проект. Бухгалтер открывает тот же адрес и видит остатки без кнопок операций. Замерщик видит резерв, только если он ответственный по проекту, и не видит общие остатки.

## Версии сущностей

`audit_log` по-прежнему список событий (вход, пароль, приглашение, роль, КП, проект, склад) без диффа полей. `GET /api/audit` не менялся.

Рядом лежит `entity_versions`: организация, тип и id сущности, автор, действие, `before_json`, `after_json`, время. Это только просмотр: отката и слияния веток нет. Таблица создаётся при старте API (`CREATE TABLE IF NOT EXISTS`), отдельная миграция не нужна.

Что пишется:

| Событие | Тип | Что в снимке |
|---|---|---|
| создание проекта | `project` | клиент, телефон, адрес, ответственный, статус, КП, сумма, срок |
| смена статуса | `project` | тот же снимок; повтор того же статуса строку не добавляет |
| привязка или снятие КП | `project` | тот же снимок, если `quote_id` реально изменился |
| сохранение КП | `quote` | тип, проём, стекло, число позиций фурнитуры, проект. Закуп и суммы в снимок не входят |
| приход, расход, резерв, снятие | `stock` | артикул, остаток, резерв, минимум. `entity_id` — `part_id` каталога |
| смена роли | `user` | роль до и после, плюс имя и email, чтобы строку было узнать |

`GET /api/versions` — последние строки. Фильтры: `entity_type` (`project`, `quote`, `stock`, `user`) и `entity_id` (только вместе с типом), `limit` до 200. CSRF на GET не нужен. Без сессии — 401.

Кто видит:

| Роль | Список версий |
|---|---|
| admin, owner | вся организация |
| остальные | только строки, где `actor_id` — они сами |

Чужая организация в выборку не попадает. Менеджер, открыв карточку, не видит правку хозяина по тому же проекту.

В ответе у каждой строки разобранные `before` и `after` и короткая `summary` вида «Статус: Создан → Просчёт».

Где смотреть в интерфейсе: блок «История» в карточке проекта (`/lk/projects.html`), на складе (`/lk/stock.html`, по выбранной позиции или последние по складу) и под сохранёнными КП (`/cfg.html`). У админа и хозяина в кабинете, рядом с полным журналом, есть таблица «Версии сущностей».

Как проверить локально (сервер с `DUSHEVYE_SERVE_PUBLIC=1`, как в блоке «Конфигуратор КП»):

1. Войдите менеджером, откройте проект и смените статус. В «Истории» карточки одна строка: было и стало по статусу.
2. Войдите хозяином или админом. В той же карточке видна и правка менеджера, и своя. В кабинете блок «Версии сущностей» собирает проекты, КП, склад и роли.
3. Снова войдите менеджером: в истории нет строк, где автор — хозяин. `GET /api/audit` при этом отвечает как раньше.

Повторяемая проверка API:

```bash
.venv/bin/python tests/test_versions.py
.venv/bin/python tests/test_stock.py

```

## Секреты

В git не коммитятся: пароль VDS, `DUSHEVYE_SESSION_SECRET`, `api.env`, `.env`, сгенерированные пароли пользователей, `*.db`. Пароль выкладки только из окружения `DUSHEVYE_VDS_PASS` или ключа `DUSHEVYE_VDS_KEY` (`deploy/deploy-vds.py`).

## Безопасность P1 (#2–6)

В коде, без выкладки на VDS и без HTTPS:

- CSRF на входе, выходе, смене пароля, приглашении, смене роли, сохранении КП (`POST /api/quotes`), проверке конфигурации (`POST /api/config/validate`), мутациях проектов и склада (`POST /api/stock/in`, `/out`, `/reserve`, `/release`). Токен: `GET /api/auth/csrf`, заголовок `X-CSRF-Token`. `GET /api/templates` токен не требует.
- Публичные `POST /api/vitrine/chat` и `POST /api/vitrine/leads` без CSRF: это гость без сессии. Лимит 10 запросов в минуту на `X-Real-IP`.
- Лимит входа: 5 попыток за 15 минут с одного IP и email, дальше `429`.
- Cookie сессии: HttpOnly и `SameSite=Strict`. Флаг Secure включается только при `DUSHEVYE_COOKIE_SECURE=1` (после HTTPS). Пока сайт по HTTP на IP, флаг остаётся выключенным.
- CSP и сопутствующие заголовки в `deploy/nginx-dushevye.conf`. В `script-src` пока есть `'unsafe-inline'` — у страниц ЛК ещё инлайновые скрипты.
- Временный пароль новой учётки показывается в модалке с копированием, не через `alert()`.

HTTPS и домен по-прежнему не делаем. Секрет сессии только из `DUSHEVYE_SESSION_SECRET`.

Подробный разбор и фазы — в `DEVELOPMENT.md`.
